# Ampara — VM Linux (SO): plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Uma VM Ubuntu Server 24.04 (QEMU + WHPX) que se provisiona sozinha no primeiro boot e sobe PostgreSQL, API, Ponte Polícia, nginx, páginas web, monitor, auditd e túnel Cloudflare, com scripts, evidências e vídeo que cobrem cada linha da rubrica de SO (PDF p.37).

**Architecture:** O Windows só cria o disco, serve o seed cloud-init (NoCloud por HTTP em `127.0.0.1`, que a VM enxerga como `10.0.2.2`) e inicia o QEMU. Dentro da VM, o cloud-init baixa o repositório e roda `infra/vm/provisiona.sh`, que executa `01`…`05` em ordem; cada script é idempotente, escreve seu log de execução e é conferido por `verifica-vm.sh`, que traduz a rubrica em asserções. A lógica do monitor e os cálculos são funções puras testáveis no Git Bash; o resto é provado dentro da VM.

**Tech Stack:** Bash (`set -euo pipefail`, shellcheck), PowerShell 5.1+, QEMU (`qemu-system-x86_64`, `qemu-img`), cloud-init NoCloud, netplan, ufw, systemd, auditd, nginx, PostgreSQL 16, .NET SDK (versão do `api/global.json`), Python 3, Node, stress-ng, cloudflared.

**Spec:** `docs/superpowers/specs/2026-11-14-ampara-design.md` (seção 6.5; 6.3 e 7.2 só para portas e variáveis). Contratos: `docs/superpowers/plans/2026-11-14-00-indice-e-contratos.md` (vence em caso de divergência).

**Cronograma sugerido:** ter 17: tarefas 1–5 (VM sobe e a infra passa em `verifica-vm.sh --criterio infra`). qua 18 manhã: 6–9 e 11. qua 18 tarde: 12 (execução limpa + evidências), 13 (README + vídeo), 10 se sobrar tempo. Gravar o vídeo na qua 18 à noite; quinta é só envio.

## Global Constraints

- VM: **Ubuntu Server 24.04 em QEMU + WHPX** (sem administrador, conta ou custo). Planos B: Hyper-V (Pedro ativa) ou VM Azure for Students. WSL2 descartado (PDF exige VM).
- "provisionado de forma automática (dentro da VM)" [PDF p.36]: cloud-init (NoCloud) no primeiro boot baixa o repositório e roda os scripts.
- `01-infra.sh`: hostname, IP fixo/gateway/DNS por netplan, usuários, ufw (inclui saída 1883 para o MQTT).
- `02-app.sh`: dependências, variáveis, build/publicação; orquestração explícita **PostgreSQL → migrations → API → Ponte → nginx** (units systemd com `After=`/`Requires=`); healthcheck que só conclui com `/health` respondendo.
- `03-monitor.sh` + serviço systemd tolerante a falhas: **CPU > 80%, memória > 80%, disco > 85%** (limites em arquivo de configuração), saúde dos serviços (incluindo a conexão MQTT da API); alertas em `/var/log/ampara/alertas.log` e no journald; `stress-ng` dispara cada alerta.
- Auditoria: `auditd` com regras sobre `/etc/ampara`, os scripts e `sudo`; log de execução de cada script (início, fim, código de saída).
- Teste de falha roteirizado: matar API e monitor → systemd reinicia → monitor registra. Túnel `cloudflared` como serviço. Evidências em `infra/evidencias/`. Vídeo ≤ 7 min [PDF p.35].
- Rubrica [PDF p.37], 10 pts: infra (redes, DNS, IP) 2 · aplicação (dependências, configurações, orquestração) 2 · monitoramento CPU/Disco/Memória 2 · monitoramento como serviço tolerante a falhas 1 · logs de auditoria e execução 1 · funcionamento completo 2. Entrega: link do repositório GitHub (scripts, configurações, evidências, README.md) + vídeo.
- Contratos: API 5080, Ponte 8000, nginx 80 com `/` página de emergência, `/painel-risco` painel Risco Cidadão, `/policia` painel da Ponte, `/api` e `/hubs` → API, `/ponte` → Ponte. Variáveis: `AMPARA_DB`, `AMPARA_JWT_SECRET`, `AMPARA_CRYPTO_KEY`, `AMPARA_DEMO`, `RISCO_CSV`, `MQTT_HOST`, `MQTT_PORT`, `PONTE_URL`, `PONTE_CHAVE_SERVICO`, `PONTE_CHAVE_POLICIA` (provisionada em `ampara.env`, hex de 32), `PONTE_DB`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` (`claude-haiku-5-5`). Nenhum nome de rota ou variável fora dos contratos. Decisões da rodada 2 que valem aqui: `GET /health` fica na **raiz** da API (`http://127.0.0.1:5080/health`; 200 = saudável, inclusive `"status":"degradado"` quando só o MQTT está fora; 503 `"falha"` se o banco não responde) e o nginx também expõe `/health`; migrations rodam com `dotnet Ampara.Api.dll --migrar` (sem `dotnet ef` na VM); `web-painel-risco` é construído com `--base=/painel-risco/`; `location /policia` leva `proxy_set_header X-Forwarded-Prefix /ponte`; units `ampara-api`, `ampara-ponte`, `ampara-monitor` e `cloudflared`; limites do monitor em `/etc/ampara/monitor.conf`.
- Nada de dado pessoal real; segredos só em variável de ambiente/arquivo `0640` fora do repositório; `.env` no `.gitignore`. Textos em português do Brasil.
- Sem Docker. Downloads grandes (imagem Ubuntu ~600 MB, QEMU, cloudflared) só com o ok do Pedro. Commits pequenos na `main`, só depois de rodar a verificação da tarefa; cada tarefa feita com IA acrescenta o prompt em `prompts.md`.
- Todo script: `#!/usr/bin/env bash`, `set -euo pipefail`, fim de linha **LF**, shellcheck sem avisos, idempotente (rodar duas vezes não muda o resultado), nunca `set -x` (vazaria segredo).
- Windows: subir processos longos (QEMU, servidor do seed) com `Start-Process`, nunca como tarefa em segundo plano; parar sempre **por PID**, nunca `taskkill /IM`.
- Convenção de comando: `vm <Acao> [...]` = `powershell -NoProfile -File infra/host/Criar-Vm.ps1 -Acao <Acao> [...]`, executado na raiz do repositório.

## Review Focus

Entradas e condições que a spec implica e que mais provavelmente quebram; cada linha tem o teste na tarefa indicada.

1. **Fim de linha CRLF** em scripts/seed criados no Windows (`bash\r: command not found`; `#cloud-config` com BOM/CR é ignorado). Esperado: todo arquivo em `infra/` em LF, seed sem BOM. Teste: Tarefa 1 (`teste-eol.sh`) e Tarefa 3 (seed).
2. **Reexecução do provisionamento** (cloud-init repete, Pedro reroda um script). Esperado: nada duplicado (regra ufw 1883 uma vez, regras do auditd uma vez) e **segredos não regerados** — trocar `AMPARA_CRYPTO_KEY` tornaria os IMEIs já cifrados ilegíveis. Teste: Tarefas 5 e 6.
3. **Broker MQTT inacessível** (HiveMQ fora do ar ou saída 1883 bloqueada). Esperado: a pilha sobe, `/health` responde, o monitor alerta `MQTT` e a VM não trava. Teste: Tarefa 11 (cenário `mqtt`).
4. **Porta do host ocupada** (8080/2222/8088 usadas por emulador, Vite ou outra VM). Esperado: erro claro em português e código ≠ 0 antes de iniciar o QEMU. Teste: Tarefa 3.
5. **Logs crescendo até encher o disco** (o monitor e os scripts escrevem sem parar; disco > 85% é justamente um alerta). Esperado: logrotate com limite de tamanho para `alertas.log`, `execucao.log`, `provisiona.log`, e alertas repetidos limitados por cooldown. Teste: Tarefas 2 e 8.
